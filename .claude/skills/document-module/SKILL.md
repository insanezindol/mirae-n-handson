# 레거시 모듈 문서화

## 원칙
- 분석 대상 폴더(`$ARGUMENTS` 의 모듈 경로)의 파일은 읽기만 한다. 수정 · 이동 · 삭제 · 실행하지 않는다.
- 산출물은 `docs/<모듈명>/` 아래 세 파일뿐이다. `<모듈명>` 은 폴더 이름이 아니라 아래 표로 정한다.

| 모듈 경로 | 모듈명 |
|---|---|
| `legacy/item-bank-php` | `item-bank` |
| `legacy/assignment-thymeleaf` | `assignment` |
| `legacy/grade-mssql` | `grade` |

- 표에 없는 경로면 멈추고 모듈명을 사람에게 묻는다. 범위 제한 인자가 있으면 그 파일 · 기능만 본다.
- 근거는 모듈 안 파일은 모듈 기준 상대 경로(`search.php:215`), 모듈 밖은 저장소 루트 기준(`db/mariadb/init/01-schema.sql:70`)으로 적는다.
- 단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어간다. 저장 전에 다음 단계를 시작하지 않는다.

## 절차
1. **계획 먼저 제시** — 모듈의 파일 목록을 훑고, 읽을 파일 · 단계별 산출물 · 범위 밖으로 둘 것을 짧게 보여 준다. 사람이 확인하면 시작한다.
2. **진입점** — 사용자 요청이 처음 닿는 파일 · URL · 컨트롤러 메서드를 표로 정리한다(진입점, 역할, 근거 줄). → `ARCHITECTURE.md` 에 모듈 개요 · 폴더 구조 · 진입점 표를 저장.
3. **의존 관계** — include/require · import · 함수 호출을 실제 호출문으로 따라가 흐름도(mermaid)와 호출 표를 만든다. 가장 긴 함수 3개와 미확인 목록도 적는다. → `ARCHITECTURE.md` 에 이어서 저장.
4. **데이터 흐름** — 모듈이 읽고 쓰는 테이블 · 뷰, 관계(mermaid erDiagram), 테이블별 읽기/쓰기 위치(파일:줄번호, SELECT/INSERT/UPDATE/DELETE)를 정리한다. 스키마 정의 파일(`db/`)도 근거로 읽는다. 관계마다 **선언**(스키마에 외래 키가 있음, FK 정의 줄) / **추정**(외래 키 없이 JOIN · WHERE 조건으로만 짐작함, 그 조건 줄) 을 구분해 erDiagram 라벨과 관계 표(관계, 구분, 스키마 근거, 코드 근거)에 적는다. 추정 관계가 하나도 없으면 "추정 관계 없음"을 적는다. → `ERD.md` 저장.
5. **비즈니스 규칙 후보** — 조건문 · SQL · 검증 코드에서 규칙을 뽑아 아래 형식으로 적는다. 주제별 절(검색 조건, 정렬 · 페이지, 등록 검증 …)로 나누고, 매직 넘버 · 주석과 코드가 다른 것 · 같은 규칙이 여러 곳에 다르게 구현된 것은 따로 모은다. → `BUSINESS-RULES.md` 저장.
6. **사람이 표본 점검할 규칙 3개 추천** — 답변 끝에 3개를 고르고 고른 이유를 한 줄씩 적는다. 반드시 **가장 그럴듯한(틀려도 눈치채기 어려운) 규칙 1개**를 넣고, 나머지는 확신도 "추정"인 규칙 · 모듈 밖 근거에 기대는 규칙에서 고른다.

## 규칙 형식
| ID | 규칙 | 근거 | 근거 코드 | 확신도 | 비고 |
|---|---|---|---|---|---|
| BR-01 | 조건이 여러 개면 모두 `AND` 로 묶는다. | `search.php:44`, `:98` | `$where .= " AND unit_code = ?";` | 확실 | OR 조합은 없다 |

- ID 는 `BR-01` 부터 순서대로 매기고, 나중에 추가한 규칙은 이어지는 번호를 쓴다(기존 번호를 다시 매기지 않는다).
- 근거 코드는 근거 줄의 코드를 그대로 인용한다. 여러 줄이면 `<br>` 로 잇고, 표 안의 `|` 는 `\|` 로 쓴다.
- 확신도: **확실** = 조건문 · SQL 로 동작을 확인함 / **추정** = 이름 · 주석 · 스키마 설정으로 짐작함(실행 미확인).
- 문서 머리에 분석 범위와 "코드를 읽어서 뽑았고 실행으로 확인하지 않았다"를 적는다.

## 하지 말 것 (item-bank 검증 이력에서 실제로 틀렸던 유형)
- **모듈 코드만 보고 결론 내기.** 공개 필터(`status = 'A'`)는 PHP 가 아니라 뷰 정의(`01-schema.sql:68-70`)에 있었고, 단원 코드 대소문자는 PHP 가 아니라 컬럼 콜레이션(`utf8mb4_unicode_ci`)과 연결 문자셋이 결정했다. 비교 · 필터 규칙은 스키마 · 뷰 · 콜레이션 · DB 설정까지 확인한 뒤 적는다.
- **주석을 근거로 쓰기.** "검색 화면에 나오지 않는다"(`register.php:84`)는 주석이었고 실제 보장은 뷰 조건이었다. 근거 줄은 실행되는 코드여야 하며, 주석 내용은 비고나 "주석과 코드가 다른 것"에만 적는다.
- **주석의 설명을 그대로 믿기.** "범위 밖 난이도는 대개 0건"이라는 주석과 달리 `05` · `3.9` · `5abc` 는 정수 변환 뒤 결과가 나왔다. 형 변환 · 정규식은 경계값을 직접 대입해 본다.
- **경계 · 예외 분기 빠뜨리기.** "1 미만은 경고 없이 1페이지", "공백만 있는 값은 경고 없음", "태그 값은 trim 하지 않음"처럼 분기마다 경고 · 보정 여부가 달랐다. 조건문의 모든 가지(빈 값 · 공백 · 음수 · 상한 초과)를 규칙이나 비고에 적는다.
- **인용 코드와 근거 줄 어긋나기.** 근거 줄 범위에 적은 조건이 인용에서 빠졌었다. 규칙 문장의 조건마다 인용 코드에 그 줄이 있는지 확인한다.
- 존재하지 않는 함수 · 파일 이름, 실제 호출문으로 확인하지 않은 호출 방향, 코드에 없는 규칙(있을 법한 검증 · 권한 체크)을 만들지 않는다. 찾지 못한 것은 "미확인"에 적는다.
