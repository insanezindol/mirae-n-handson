# 머지 전 검증

검증 대상: $ARGUMENTS

- 인자가 비어 있으면 `git diff upstream/main...HEAD` 를 검증 대상으로 삼는다.
- 인자가 patch 파일 경로면 그 patch 를, git 범위 · 브랜치면 그 diff 를 대상으로 삼는다.
- 이 Skill 은 만든 쪽이 아니라 검증하는 쪽이다. 배경은 저장소 루트의 `templates/verification-loop.md` 에 있다.

## 원칙

- 코드를 수정하지 않는다(tester 가 추가하는 테스트 파일은 예외). 판정과 이슈만 보고한다.
- 근거 줄번호를 댈 수 없는 지적은 하지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다.

## 1. 요청 범위 확인

- 이 변경이 무엇을 요청받아 만든 것인지 한 문장으로 확인한다. 인자나 대화에 있으면 그것을 쓴다.
- 주어지지 않았으면 판정하지 말고 먼저 질문한다. 커밋 메시지나 diff 에서 요청을 추측해 채우지 않는다.

## 2. 변경 파일 목록과 diff 읽기

- 목록을 먼저 본다: `git diff --stat <범위>`. patch 파일이면 `git apply --stat <patch 경로>`.
- 이어서 파일마다 diff 를 읽는다. 줄번호 근거가 필요하면 해당 파일을 Read 로 앞뒤 문맥까지 읽는다.
- 변경 파일이 없으면 "검증할 변경 없음"이라고만 답하고 끝낸다.

## 3. 체크리스트 대조

- 이 단계는 직접 하지 않고 `reviewer` Sub-agent 에 위임한다. 비교 범위(검증 대상)와 1단계의 요청 범위 문장을 바꾸지 않고 그대로 넘긴다.
- reviewer 가 아래 기준으로 대조해 항목별 표시와 이슈 목록(`파일:줄번호` 포함)을 돌려준다.
- 저장소 루트의 `templates/approval-checklist.md` 를 읽고, 그 파일의 항목마다 충족 · 미충족 · 확인 필요 중 하나로 표시한다.
- 항목과 심각도 정의는 그 파일이 기준이다. 여기에 옮겨 적지 않으며, 파일이 바뀌면 바뀐 내용을 따른다.
- 컨벤션 항목은 저장소 루트의 `CLAUDE.md` 와 대조한다. `convention-check` Skill 을 쓸 수 있으면 그 결과를 쓴다.
- `reviewer` Sub-agent 가 없는 환경에서는 기존 방식대로 이 단계를 직접 수행한다.

## 4. 테스트 실행

이 단계는 직접 하지 않고 `tester` Sub-agent 에 위임한다. tester 는 변경된 폴더의 테스트만 실행한다.

| 바뀐 곳 | 실행 위치 | 명령 |
|---|---|---|
| `modern/api` | `modern/api` | `./gradlew test` |
| `modern/web` | `modern/web` | `npm test` |
| 이관 코드 | `characterization` | `npm test` (레거시 대상) |
| 이관 코드 | `characterization` | `TARGET_BASE_URL=http://localhost:8080 npm test` (새 API 대상) |

- 새 로직(새 public Service 메서드 · 새 엔드포인트 · 바뀐 동작)에 테스트가 없으면 tester 가 테스트 파일을 추가한 뒤 실행한다. 테스트 파일 외의 소스 코드는 고치지 않는다.
- tester 에게서 실행한 명령, 통과 · 실패 수, 실패한 테스트 이름, 추가한 테스트 파일 목록을 돌려받는다.
- 사용량 절약: 출력은 통과 / 실패 수와 실패한 테스트 이름만 남긴다. 전체 로그를 대화에 싣지 않는다. 로그가 길면 파일로 돌려 놓고 요약 줄과 실패한 케이스만 읽는다.
- 실행할 수 없었으면(서버 꺼짐, 의존성 미설치) 그 사실과 못 돌린 명령을 적고 사람에게 기동을 요청한다. 그 기준은 충족으로 표시하지 않는다.
- patch 파일은 적용하지 않은 상태에서는 테스트를 돌릴 수 없다. 작업 트리에 적용해도 되는지 사람에게 먼저 묻는다.
- 테스트를 통과시키려고 테스트 코드나 `characterization/__snapshots__/` 를 고치지 않는다.
- `tester` Sub-agent 가 없는 환경에서는 기존 방식대로 이 단계를 직접 수행한다(이때는 테스트 파일을 추가하지 않는다).

## 5. 승인 기준 판정

- reviewer 와 tester 의 보고를 모두 받은 뒤, 메인 세션이 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 최종 판정한다. Sub-agent 의 판정을 그대로 옮기지 않는다.
- reviewer 와 tester 의 보고가 엇갈리면 엇갈린 지점을 양쪽 보고 그대로 적고, 판정하지 말고 사람에게 묻는다.
- 네 기준이 모두 충족이어야 승인이다. 하나라도 미충족이면 반려다.
- 요청 범위를 모르는 상태에서 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.

## 출력 형식 (순서 고정)

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수, 실패한 테스트 이름 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
|---|---|---|---|---|

확인 필요
- 줄번호 근거를 댈 수 없었던 사항과 그 이유
```

- 이슈 한 건은 심각도(치명 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 순서로 적고, 네 항목을 모두 채운다.
- 파일 경로는 저장소 루트 기준 상대 경로로 적는다.
- 이슈가 없으면 표 대신 "이슈 없음" 한 줄, 확인 필요가 없으면 "확인 필요 없음" 한 줄만 적는다.

## 하지 말 것

- 코드를 수정하지 않는다(tester 가 추가하는 테스트 파일은 예외). 고치기 시작하면 만든 쪽이 된다.
- 근거 줄번호를 댈 수 없는 지적은 하지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다.
- 전체 테스트 로그나 diff 전문을 답변에 붙이지 않는다.
