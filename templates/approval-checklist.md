# 승인 체크리스트 v1

v1 · 2회차 (2026-10-06)

오늘 바뀐 점
- 테스트 기준을 "충분하다"에서 public 메서드별 정상 · 오류/경계 테스트와 버그 수정 회귀 테스트로 바꿨다.
- 치명 이슈를 네 가지(비밀값 노출, 복구 수단 없는 데이터 삭제 · 손상, 인증 · 인가 우회, 외부 입력을 이어 붙인 SQL)로 못 박았다.
- 범위 밖 변경과 컨벤션 위반을 반려 사유와 경고 사유로 나눴다(네이밍 위반만으로는 반려하지 않는다).

AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다. 모든 항목은 예 / 아니오 / 확인 필요 중 하나로 답한다. 조건이 붙은 항목은 조건에 해당하지 않으면 "해당 없음"으로 적고 '예'로 센다.

네 기준의 **반려 항목이 모두 '예'** 여야 승인이다. 하나라도 '아니오'면 반려. '확인 필요'가 남아 있으면 승인하지 않고 확인부터 한다.

## 심각도 정의

- **치명** — 아래 네 가지 중 하나. 1건이라도 있으면 반려.
  1. 비밀값(비밀번호 · 토큰 · 키)이 소스 코드나 로그에 노출된다.
  2. 복구 수단 없이 데이터를 삭제하거나 손상시킨다.
  3. 인증 · 인가를 우회한다.
  4. 외부 입력을 연결하거나 보간해 SQL 을 만든다.
- **경고** — 반려 항목은 아니지만 기록해 둘 문제. 이슈 목록에 남기며, 경고만으로는 반려하지 않는다.
- **제안** — 더 나은 방법이 있다는 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다.

## 1. 테스트 통과

- [ ] 변경된 모듈의 테스트 명령을 실제로 실행했다(실행하지 않고 통과라고 쓰지 않는다).
- [ ] 변경과 관련된 기존 테스트의 실패 · 오류가 0건이다.
- [ ] 기존 테스트를 지우거나 건너뛰게(`skip`, `@Disabled`) 바꾼 곳이 없다.
- [ ] 새로 추가하거나 동작을 바꾼 public 메서드마다 정상 입력을 검증하는 테스트가 1개 이상 있다.
- [ ] 같은 메서드마다 오류 입력 또는 경계 입력을 검증하는 테스트가 1개 이상 있다.
- [ ] 테스트가 없는 public 메서드는 검증 · 계산 로직이 없는 getter · setter · 생성자뿐이다.
- [ ] 버그 수정이라면, 수정 전 코드에서 실패하고 수정 후 통과하는 회귀 테스트가 있다.

## 2. 치명 이슈 0건

- [ ] 비밀번호 · 토큰 · 키가 소스 코드(설정 파일 · 테스트 픽스처 포함)에 리터럴로 들어 있지 않다(실습용 더미 `app-pass` 제외).
- [ ] 로그 인자에 비밀번호 · 토큰 · 키 값이 들어가지 않는다.
- [ ] 데이터를 삭제하거나 덮어쓰는 코드가 새로 생겼다면, 복구 수단(백업, 상태 코드로 하는 삭제, 트랜잭션 롤백 중 하나)이 있다.
- [ ] 인증 · 인가 검사를 지우거나 건너뛰게 만든 곳이 없다.
- [ ] 외부 입력을 문자열 연결 · 보간으로 넣어 만든 SQL 이 없다(파라미터 바인딩 사용).

## 3. 요청 범위 이탈 없음

- [ ] 요청 문장이 한 문장으로 확인되었다(없으면 판정하지 않고 먼저 묻는다).
- [ ] 변경 파일마다 요청된 기능 · 버그 수정 또는 그것을 검증하는 테스트에 필요한 변경이 1줄 이상 있다.
- [ ] 요청과 무관한 변경 줄은 변경한 파일 안의 미사용 import 삭제와 import 순서 정리뿐이다.
- [ ] 무관한 리팩터링 · 전체 포맷 변경 · 의존성 업데이트가 0건이다(있으면 별도 PR 로 분리하도록 돌려보낸다).
- [ ] 의존성 추가 · DB 스키마 변경 · 설정 파일 변경이 있다면 요청에 포함돼 있었다.

## 4. 컨벤션 준수

팀 `CLAUDE.md` 의 코딩 컨벤션과 금지 사항을 대조한다(`convention-check` Skill 이 있으면 그 결과를 쓴다).

### 반려 항목

- [ ] 계층 간 의존 규칙 위반이 없다(Controller → Service → Repository 방향, Controller 의 Repository · SQL 직접 사용 없음, 다른 도메인 Repository 주입 없음).
- [ ] 빈 `catch` 블록이 없다.
- [ ] 운영 코드(`src/main`)에 `System.out` · `System.err` 사용이 없다.
- [ ] 운영 코드(`modern/web/src`, 테스트 파일 제외)에 `console.log` 가 없다.
- [ ] 검증을 통과시키려고 테스트 단언 · 예외 처리를 지우거나 건너뛰게 한 변경이 없다.
- [ ] 팀 `CLAUDE.md` 의 "금지 사항" 중 "하지 않는다" 목록에 해당하는 변경이 없다.

### 경고 항목 (기록만 하고, 이것만으로 반려하지 않는다)

- [ ] 네이밍 규칙 위반이 없다.
- [ ] 위 반려 항목에 없는 팀 `CLAUDE.md` 컨벤션 위반이 없다.

## 판정 형식

첫 줄에 `판정: 승인` 또는 `판정: 반려`. 이어서 네 기준의 충족 · 미충족 표, 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향). 기준 하나는 그 기준의 반려 항목이 모두 '예'일 때 충족이다. 코드는 수정하지 않는다.
